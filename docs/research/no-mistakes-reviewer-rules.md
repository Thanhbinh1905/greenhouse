## Findings, fixes, and repeat rounds

- **Seen:** findings contain `id`, `severity`, `file`, `line`, `description`, `action`, and optional `review_scope`; the envelope adds `summary`, `reviewed_paths`, risk level/rationale/scope, and answer-round withdrawals. There is no dedicated style category in the reviewer contract. [T:190-215,296-337; R:347-374]
- **Seen:** the model assigns `error` for must-not-merge issues, `warning` for follow-up-worthy issues, and `info` for nice-to-have items. It independently classifies `ask-user`, `auto-fix`, or `no-op`; risky or scope-expanding remedies require `ask-user`. [R:350-365]
- **Seen:** warnings as well as errors set `NeedsApproval`; `no-op` does not exempt a warning from this severity check. Missing changed-file coverage also parks an otherwise clean pass. Calling subjective findings warnings would therefore not keep them out of blocking gates. [F:81-88; R:510-531]
- **Inferred:** until there is a separate policy channel, touched-hunk-only wording and `info`/`no-op` can request advisory results, but cannot guarantee separation or model compliance. `review.path_instructions` alone cannot override the built-in ban on styling. Do not map subjective prose preferences to correctness errors. [R:347-369; D:444; F:81-88]
- **Seen:** review and fix are distinct invocations. Fixing receives selected prior findings and user guidance, then commits corrections and rereviews. The fixer already says not to add comments explaining fixes, but that is narrower than Posse's comment policy. [R:134-190; F:333-381,414-469]
- **Seen:** reviewers are fresh after code changes; only a same-pass answer finalization can resume its reviewer session. Fixer sessions may persist. Every rereview rebuilds the full review prompt, including matched path rules; the initial fixer prompt does not include them. [R:56-78,134-175,257-267,393-420; AR:130-143]
- **Seen:** invalid analyzer JSON retries the same turn prompt plus a validation note, at most three attempts. A successful outcome records the target SHA as `ReviewApprovedHeadSHA`; fix commits update the run's head, so later reviews inspect a new candidate rather than preserving the old commit identity. [R:193,449-478,538-540,659-662; F:364-381]
- **Inferred:** recorded target SHAs are evidence labels, not a read-only sandbox. Native adapters permit broad execution by default, and memory-file restrictions explicitly call themselves prompt contracts. Posse should bind its own findings and decisions to an exact candidate SHA and independently enforce write authority.
